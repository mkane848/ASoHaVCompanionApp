The Character Sheet

A companion app and content admin for ASoHaV — plan for approval, draft 4

Architecture decided · phases 0–2 built · consistency pass against Mike’s review

Draft 2 raised seventeen conflicts between your two schemas, the five rules documents, and the paper sheet. You've answered all seventeen. This draft turns them into the model I'll actually build, so §3 is now a record of decisions rather than a list of questions.

Two of your answers changed the architecture rather than just a field, and they're worth reading before the rest: Bonds and Rapport are shared objects, not character properties (§2) — which is the correct model, and which Mike’s real-time requirement now makes mandatory rather than merely tidy. And consolidating repeated fields into base classes (Issue 6) let me collapse a fair amount of the schema.

What's left open is no longer conflicts — it's four entities that don’t exist yet and that the sheet needs (§4). All four are now specified — and since drafts 3 and 4 they have been built: the seeded library, the storage contract, and the working sheet all exist. What remains open is no longer the model but the two infrastructure questions Mike’s architecture raises, in §1.

1Architecture

Decided — supersedes drafts 1–3

Mike has settled this: Vite + React 19 + TypeScript, with zustand for local UI state and TanStack Query for server state. Shared resources — Kin and Rapport — sync in real time across players, and the GM can peek at any PC's sheet and see live data.

That closes the question the first three drafts kept open. Both of those requirements are inherently multi-user, so the local-first rehearsal is off the table — there is no version of live sync or GM peek that works out of one browser's storage. We are building server-backed from the start.

What this changes

Less than it might look like, because drafts 1–3 deliberately kept the seams clean for exactly this move.

  • The data model is unaffected. Every resolution in §3 stands. Promoting Bonds and Rapport to shared, table-owned objects (§2) was the right call under localStorage and is now required — they become server records with subscriptions, exactly as modelled.
  • store.js becomes the query layer. The async adapter in the prototype was written so localStorage could be swapped for fetch() in one file. That swap is now TanStack Query hooks, and the shape of every call survives.
  • The JSON export format stays the contract — now the API's wire format rather than a file you pass around, and still what your friend's GM tooling reads.
  • The built prototype remains useful as the interaction and visual reference. It is not the shipping client; it is the spec for one.

Both decided

Offline is not required. The sheet assumes connectivity; optimistic writes and reconciliation are logged as a possible future improvement, not v1 scope. Worth knowing the consequence: a table that loses signal loses the sheet, so it is worth someone keeping the paper version in the bag.

Bond edits use a confirmation handshake. Creating a Bond, marking Kin, spending Kin, or Forging all send a proposal to the other PC, and the change only lands once they accept. A Bond holds at most one pending change — while one is outstanding, further proposals on that Bond are rejected. This makes the shared record honest by construction: there is no last-write-wins race because there is only ever one write in flight.

Scope note

This is now a genuine engineering build rather than a prototype with a storage adapter. I produce the interface, the client-side logic, and the contract it speaks — the server, auth, and real-time infrastructure are work for you, Mike, or Claude Code. §8's phasing still holds, but Phases 3 and 4 now assume the server exists.

4The four new entities

Playbooks and Party Playbooks are out per your feedback, which removes two entities and simplifies three others: Advancements become a single global list gated by tier rather than a per-playbook one, Abilities are no longer owned by a playbook, and Bond Moves stop being library content altogether.

That leaves four things to define. Three are small. The fourth — Ability — is the one that needs real thought, because you've asked it to carry the full range of PbtA effects.

ArmorType settled

: LibraryEntity + Key: ENUM(Physical, Heavy, Special). Special is one type, not a family. Camp refresh is all-or-nothing, so it's a single action on the Armor panel rather than a per-box reset.

Advancement settled

: LibraryEntity + Tier: int (1–4), Track: ENUM(Potential, Rapport), Repeatable: bool, MaxTimes: int?, Effect.

One global list, filtered by track and by your unlocked tier. Repeatable handles "some can be taken more than once"; MaxTimes is nullable so a repeatable advancement can be unlimited or capped. In the picker, a non-repeatable advancement you already hold greys out rather than disappearing — you can still read what you took.

BondMove no longer a library object

Since the two PCs write it together, there is nothing to author in the admin panel. It becomes play state on the shared Bond record: BondMoves: [{Level: int, Text: string, AuthoredAt}]. When a pair reaches a new Bond Level, the sheet opens a text field on both their sheets and stores one copy.

Ability needs the most structure

You asked for something flexible enough for PbtA — permanent Virtue boosts, +2 Ongoing, and "other things". The trap here is obvious: model it too loosely and it's a wiki page with no mechanical hooks; model it too tightly and the first ability you write won't fit.

The approach

Prose is authoritative; structure is optional metadata. Every Ability carries human-readable rules text that is always displayed and always correct. Alongside it sits a list of structured effects — zero or more — that a future rules engine can act on, and that the sheet uses today only for things it can safely do without judgement.

This means an ability that doesn't fit the structure still works perfectly: you write the prose, add no effects, and it displays like any other. Nothing is ever blocked on the model being expressive enough. And when you later build the engine, the abilities that do carry effects light up without a migration.

Ability : LibraryEntity + RulesText: string (required, authoritative), Acquisition: ENUM(Starting, Advancement, Item, Bond, Other), Tags: string[], Effects: AbilityEffect[].

5The character sheet

All data preserved, layout reorganised for screen. Responsive across phone, tablet, desktop.

Layout

Phone — one scrolling column under a sticky tab bar: Sheet · Status · Theme · Kit · Growth, with the Moves drawer reachable from every tab. The hot path at the table — mark a Condition, move a Status rank, tick Armor — is one tap from anywhere.

Tablet and desktop — two columns, no tabs. A persistent left rail holds identity: name, level, Looks, and the Virtues/Conditions table, which never scrolls away because every roll touches it. The right column scrolls: Statuses & Armor → Theme → Load → Advancement.

Panels

PanelTreatment
Virtues & ConditionsThe table is the control. Tap a Condition to mark it: the row takes an ink wash and reveals its Clear Action inline. The effective modifier shows beside the score — a Conditioned Wit +1 reads +1 → −1 — floored at −3. At 5/5 marked, a Dishonored badge appears on the panel header. Essence and usage text collapse behind an ⓘ disclosure.
StatusesTwo groups, Positive and Negative, driven by polarity. Each row is a name plus a six-pip magnitude stepper, tappable up and down, clearing at zero. Negative pips ink red-brown, Positive gold. Link to and Affected by render as visibly-inert placeholder buttons. A Camp action offers the differential clear (2D6 Negative / 1D6 Positive) as a prompt, not an automation.

ThemePick a Theme; its description and Starting Quest render live from the library. Accepted Quests list beneath with completion checks and an accepted-date, ready for the staleness rule when you design it.
LoadLight / Normal / Heavy as a segmented choice, each showing its computed capacity (base + Might). Below, the full inventory: a carry toggle per item, its Load cost, and a charge pip row where relevant. Carried weight totals against the chosen tier; over-limit is a soft warning. Latching until Camp is shown as state, not enforced as a lock.
AdvancementPotential as five pips on the sheet. Filling it opens a tier-filtered picker over the global Advancement list and resets to zero, as you specified; repeatable advancements stay in the list, others grey out once taken. Rapport renders live from the shared Party record, updating in real time as others spend it. Kin behaves differently: every Bond change is a proposal — the row shows an awaiting-confirmation state until the other player accepts, and is locked against further edits while that is outstanding. The Bond table lists one row per party member: Kin track, Bond Level, and the Bond Moves — the latter authored by the two players in a text field when a Bond Level is reached.
Moves drawerSearchable, filtered by Virtue, showing all three tiers and the Player Variant where one exists. Choice-lists render as lists now that Result carries options. Read-only — no rolling in v1.

The enforcement line

Shape enforced, legality warned. A track has five pips; a rank can't go below zero; filling a track prompts a choice. But you can exceed your Load, break the Virtue spread, or take an unearned advancement — each shows a quiet warning and lets you proceed. Confirmed in draft 2, restated here because it governs every panel above.

6The admin panel

  • CRUD on every library type, generated from schema definitions rather than hand-built per type — so the four new entities in §4 cost a config entry each, not a screen each.
  • Bulk JSON import/export, whole-library and per-type. Also the seeding path for your existing docs.
  • Change history — {who, when, objectType, objectId, before, after} per write, with a per-object timeline, field-level diff, and a global feed. With real accounts, attribution is genuine rather than self-declared.
  • Reference validation — orphaned Quests, Advancements with no tier, Items granting a nonexistent ArmorType.
  • Preview on sheet — render any object as a player will see it, without leaving the editor.

7Visual direction

Classical, pushed toward parchment and ink. Mike's note reframes this well: the game is about found family and self-discovery, and about players writing their stories together. So the sheet should read as a document being written in, not a form being filled out — and that is a stronger idea than the restraint drafts 1–3 argued for.

Leaning in

  • Parchment as a real surface, not a background colour — a warm, slightly uneven ground with subtle tone variation, so panels feel like leaves of the same book rather than cards on a page.
  • Ink as the only mark-making language. Every track, pip, clock and box is drawn as a pen stroke: hollow circles that fill, hairline rules, a marked Condition as a wash bleeding across the row. Nothing in the interface should look like a checkbox or a progress bar.
  • Marginalia. Clear Actions, quest notes, and Bond Moves — the parts the players author themselves — set in a lighter, more handwritten register, sitting in the margin rather than in the column. The Bond Move field in particular should feel like writing in a book you share.
  • Illuminated detail at section heads — versal capitals and gold rule-work, used sparingly enough that it stays a rhythm rather than decoration.
  • The Theme panel carries the most weight, since it is where the character's story actually lives. It should read like a title page.
  • The page gets ruined as the character does. Marked Conditions and negative Statuses progressively dirty their own panels — warm blotching, stain, and a roughed-up grain over the parchment, as though the book itself is taking the damage. It is the clearest way to make a sheet feel authored and lived-in rather than filled out.

How the damage is implemented

Quantised into four tiers per panel rather than a continuous value, so each overlay carries a literal opacity and paints on the first frame. Marked Conditions drive the Virtues panel, one tier each. Total negative Status ranks drive the Statuses panel, one tier per three ranks accumulated. Opacity caps at 0.62 — a badly-off character's sheet must stay readable, which is the constraint that matters more than the effect.

Still holding the line on

No dragons, no wood grain, no torn or burnt edges, no faux-leather, no drop shadows pretending to be a physical object on a desk. The distinction: parchment and ink are the medium the characters' stories are written in — they are not a costume the UI wears. Texture earns its place when it makes the writing feel real; it fails when it makes the app look like a prop.

The sheet as built uses the restrained version of this. Pushing it further is a small, self-contained pass — it is on the list.

9Risks

  1. The Bond handshake trades speed for correctness. The one-pending-change rule removes write conflicts entirely, but it means no Kin change is instant, and a player who is away from the table can block their partner’s sheet. It needs an expiry or a cancel affordance, or it will be the thing people complain about first.
  2. Combat will reshape the sheet. Statuses, Armor and Load are all combat-adjacent. Panels are built independently so a Combat panel drops in — but expect churn, and don't over-polish before it lands.
  3. The Ability effect model is the one speculative piece. §4 proposes a flexible structure covering the PbtA patterns in your rules, but you have not written the abilities yet — the first real batch will test whether it holds.
  4. Schema migrations become a standing cost now that data is live and the rules are still drafts. Keep library content as data rather than markup, so a rules change stays an import rather than a rebuild.

Phases 0–2 are built. The next build step is Phase 3, the admin panel — which is independent of the sheet and is what makes the abilities-at-creation setting editable. Phase 4 needs the server. Both of §1’s open questions are now settled, so nothing blocks Phase 3 — say the word and I’ll build it. The one decision still worth making before Phase 4 is how a pending Bond proposal gets released: an expiry, a cancel for the proposer, or both.
